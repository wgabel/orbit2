# Orbit 2 contributor instructions

## Working with the repository

- Start with [ORBIT2-ARCHITECTURE.md](ORBIT2-ARCHITECTURE.md), the short overview and task routing index. Read relevant feature modules, source code, tests and any other material that helps solve the task. The routing table is advisory, not an allowlist or a limit on context; cross-cutting work can require several modules. Do not load every specification by default. Adjust the depth of investigation to the complexity and risk of the task.
- Use [ROADMAP.md](ROADMAP.md) and its linked milestone registers when planning or changing implementation status. Use [README.md](README.md) for practical build/run instructions. The implementation and tests are the evidence for current behavior; reconcile stale documentation instead of assuming that every design proposal is implemented.
- For musical patch or composition tasks, the [generative ambient composition guide](docs/examples/generative-ambient-composition.md) distinguishes individual sound/effect design from whole-piece layering and arrangement. Consult it when relevant to the musical goal; it is not a required template or a constraint on genre, feature design, or exploration.
- For harmony, tuning, melody, timbre, perceived loudness, spectral balance, depth and musical quality decisions, consult the relevant sections of the [music theory and electronic sound design guide](docs/examples/music-theory-and-sound-design.md). Use its examples and quality checks as adaptable musical guidance, not stylistic restrictions or evidence of listening verification. Check real node capabilities before building patches.
- For genre-oriented sound design or musical composition, start with the [electronic music genre index](docs/examples/electronic-music-genres.md). Select relevant genre families and [Orbit 2 musical techniques](docs/examples/genres/orbit-techniques.md) as useful, then follow the appropriate theory, arrangement and technical contracts. These are musical reference points, not an exhaustive genre list, required reading of every family, or constraints on novel music. Distinguish authentic production techniques from feasible approximations; verify current capabilities and the resulting music.
- For finished voices and presets, use [sound quality and voice design](docs/examples/sound-quality-and-voice-design.md): avoid exposed raw noise and hollow/basic test-tone timbres in polished music unless musically intentional; shape noise, layer or filter the tonal source, articulate brightness and compare the voice in context. Pure sine is useful for a clean sub, partial or control signal, not a default foreground instrument. Protect the user's intended musical style and successful arrangement; improve the palette when feedback is about sound quality.
- For evolving voices and musical foundations, consider deliberate interactions between nodes: shared or offset modulation, overlapping partials, nonlinear shaping and different timescales can produce emergent harmonic shifts and coordinated breathing. See the [breathing harmonic drone](docs/examples/foundations/breathing-harmonic-drone.md), the first listener-validated reference foundation. Use its principle where musically useful; the recipe, complexity and style are optional. Explore other ways to create sounds and document successful new foundations.
- For complete musical pieces and substantial sound-design work, use the [mixing, mastering and analysis guide](docs/examples/mixing-mastering-and-analysis.md). Where feasible, render a baseline (prefer the native engine; label independent previews), measure master and important voices across representative sections/full duration, identify problems, refine purposefully, then re-render and compare at matched levels. Check actual sound quality when listening is available; otherwise distinguish user listening feedback, objective measurements and hypotheses. Do not infer that a tone sounds good or noise is unobtrusive from RMS/peak alone, claim unsupported mastering processors, or require unavailable tooling to start creative work. Scale analysis to the task; report the evidence, changes and remaining limitations.
- When balancing melody, accents or other competing roles in a substantial piece, consult [contextual layer balance](docs/examples/contextual-layer-balance.md). Where feasible, compare aligned post-voice-fader roles against their simultaneous backing in representative short windows (including sparse and dense sections), preserve intentional rests and dynamics, and validate targeted changes on comparable windows. The research and case study offer diagnostics, not mandatory dB targets, equal-loudness rules or a requirement for unavailable tools.
- Respect established architectural boundaries and stable identifiers, while remaining free to propose and implement justified architectural improvements within the user's requested scope. Documentation guides decisions; it is not a substitute for engineering judgment.
- A new task may have no matching document or roadmap entry. Explore adjacent contracts and the code, design the new capability, and continue within the authorized scope. Extend the closest module or create a new one when that makes the knowledge easier to find; add or revise the index and roadmap if relevant. Do not require a separate documentation PR, a previously assigned milestone, or a fixed directory/template before beginning work.

## Documentation and verification

- For every implementation PR (feature, improvement or fix), record its actual linked PR number in the relevant implementation description and milestone register: `[PR #N](https://github.com/wgabel/orbit2/pull/N)`. Update the roadmap summary/index where applicable. For a small fix with no milestone, a concise record in the relevant feature module and appropriate register is sufficient. Keep earlier PR evidence and add follow-ups.
- If the number is unknown, open the PR and then add the links to the same branch before merge. Distinguish planned, partial, in-review and merged work; never cite a documentation-only PR as implementation evidence. For older direct-to-main changes, cite the actual commit rather than inventing a PR.
- Prefer one authoritative technical contract with relative links from related modules; avoid duplicating detailed specifications. Preserve useful rationale, examples and historical implementation records, clearly distinguishing them from current contracts. Split or combine modules when the topic warrants it; filenames and target sizes are not rigid requirements.
- Add regression coverage for changed behavior and report what was actually verified. Scale testing and documentation to the change; a typo or a purely editorial correction need not create a new feature specification.

## Task handoff: documentation feedback

At the end of every task, include a short documentation report in the user-facing summary (or to the coordinating agent when delegated):

- **Documentation consulted:** List the repository-relative paths of Markdown files actually read for the task, including this file, the overview, roadmap and any feature modules consulted. If only specific sections were read, indicate that when useful. Do not claim to have read files you did not inspect. If none were consulted, say so.
- **Documentation discoverability:** Report whether finding the relevant information was straightforward. Mention any missing topics, unclear navigation, misleading links, conflicting or outdated descriptions, or other search difficulties that affected the task. Say how the gap was resolved (for example, inspecting the source or tests), and flag any useful documentation improvement. If there were no difficulties, say "No issues found."

Keep this report proportionate and factual, including for read-only tasks. It is feedback on the documentation system, not a requirement to read additional files or a reason to delay work on a new topic. When coordinating multiple agents, collect their reports and consolidate the relevant paths and findings in the final handoff.
