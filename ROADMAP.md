## Reading guide and current implementation

**Status vocabulary:** Implemented = verified on the audited main branch or in an explicitly identified implementation PR; Partial = a defined subset delivered; In progress = implementation underway; Planned = design or future deliverable; Deferred = deliberately outside current scope.

**Implementation traceability (mandatory):** Every delivered feature, improvement and bug fix must cite its actual implementation pull request(s) using `[PR #N](https://github.com/wgabel/orbit2/pull/N)` directly in the relevant implementation description and roadmap entry, and in the status table when applicable. Include follow-up PRs beside the affected feature. Open the PR first if its number is not known, then update the architecture on that PR's branch before merge. Never substitute a documentation-only PR for runtime evidence or mark unmerged work as merged. Older direct-to-main implementations predating the PR workflow have no PR number; cite the actual commit when extending their implementation record. Do not invent historical PRs.

## 13. Implementation roadmap

Do not attempt to build the entire modular synth in one change. Establish and test each foundation.

**Performance-first priority for stereo/unison:** deliver Phase 7.3.1 passive monitoring, 7.3.2 compiler/runtime/resource diagnostics and the 7.3.4 reproducible DSP benchmark baseline before Phase 7.5. Measure the existing mono graph and then compare voice counts, channel expansion and graph-swap peak load. Use external live renderer profiling when reliable in-app DSP timing is unavailable; 7.3.3 is recommended for UI work, while 7.3.5–7.3.6 can progress independently. See [stereo/unison design](docs/audio/stereo-panning-and-unison.md#1-performance-first). This is a dependency-aware priority, not a blocker for unrelated feature tracks.

**Realistic instrument priority:** [Faust-first physical modelling](docs/instruments/realistic-instrument-emulation.md) (7.2.7) responds to user feedback that existing instrument approximations lack realism. Begin with exact dependency/license clearance and one or two native Faust proofs of concept; independently audition Hammond/pipe-rank and rotary recipes with existing nodes. Follow the 7.3 performance baseline and 7.6 listening acceptance before expanding; keep old preset IDs.

**Sound-design priority:** start the [instrument audition track](docs/roadmap/advanced.md#phase-76--instrument-and-sound-design-and-audition) with the small existing-node test fixture and candidate sounds across genres now; do not postpone the listening work until stereo or sampling ships. Preserve the 7.3 performance-first priority for expanded DSP. Prioritize Note-mode articulation (7.2.8d) and reusable modules (7.4.3–7.4.5) to simplify this workflow, and pursue samples, multisamples, instrument models and production processing based on A/B feedback.

**Completed urgent fix:** dynamic signal tap allocation (6.18.8, [PR #20](https://github.com/wgabel/orbit2/pull/20)) merged. Preserve the regression: a single visible plot on a reachable signal must work even in a large patch; capacity limits simultaneous observed signals, not graph size. Dedicated analyzer sinks and Phase 7.3 remain separate future work.

The most direct drone-performance path is 7.2.2 and 7.2.8a–b (delivered) → 7.2.8c (delivered, [PR #19](https://github.com/wgabel/orbit2/pull/19)). Gated instruments depend on rhythmic sources, ADSR and monophonic note delivery. Presentation-only annotations, dedicated analysis and the post-mixer pitch shifter can proceed independently.
