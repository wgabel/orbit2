# GPU rendering efficiency and resource management — agent implementation guide

**Status:** Research and implementation guidance, not implemented architecture. PixiJS + PixiUI + PixiJS Layout is the owner-selected preferred stack for prototyping; pin compatible versions and verify API behavior, license, browser capabilities and build integration during S3/S4. See the [technology direction](gpu-renderer.md#selected-technology-direction-and-implementation-rules). The production go/no-go gate remains S5. ## Why this matters (Unity lesson)

Unity UGUI can spend significant CPU time regenerating canvas batches when one element changes. See [Unity UI optimization](https://unity.com/how-to/unity-ui-optimization-tips). A WebGL surface is not inherently immune: layout, traversal, hit testing, texture upload, triangulation, batch breaks, fill rate and resource churn still cost time. The goal is to keep independent visual state cheap, reuse immutable resources, update only affected data, and draw efficiently. Rendering a new frame is distinct from rebuilding its geometry, layout, text or cached textures. A new frame generally draws all visible content again unless an explicit compositing/caching design avoids that work. Do not assume render groups are independently persistent screen buffers.

## Native PixiJS features to evaluate and reuse

Prefer supported engine mechanisms over a parallel texture cache, batching engine or scene graph. Keep custom abstractions narrow and justified by Orbit-specific ownership, policy or test seams.

| Mechanism | Use in Orbit | Important limitation |
| --- | --- | --- |
| Shared Texture/TextureSource and Assets | Repeated backgrounds, port glyphs, control icons, knobs | Many sprite instances can reference one texture source; position/tint/scale remain independent. Shared texture alone does not guarantee one draw call. |
| Spritesheets/atlases | Group common UI glyphs and icons by compatible lifetime/sampling; use tint where appropriate | Respect hardware limits, padding, DPI/zoom readability, mip/filter settings, asset licensing. Do not pack unique per-node text into unbounded atlases. |
| Automatic batching | Compatible sprites and simple graphics | Blend state, masks, filters, texture slots, shaders, order and render group boundaries affect batch breaks. Never reorder overlapping content incorrectly merely to reduce calls. |
| GraphicsContext | Shared immutable vector geometry for node shells, controls and port shapes | Context mutation affects all consumers. Own shared contexts separately; do not destroy them when a view is removed. Compare vector vs sprite/nine-slice at zoom extremes. |
| BitmapText / SDF or MSDF fonts | Fast changing numbers, repeated labels and glyphs | Verify font coverage, precision, accessibility, line breaks, legibility at zoom/DPR, user aliases and non-Latin fallback. Do not re-rasterize unchanged strings per frame. |
| Render groups | World camera and a few coarse groups with different update patterns | Parent transforms can be cheap; structural changes and group proliferation cost CPU and inhibit cross-group batching. Not one group per node. |
| cacheAsTexture / generated shared texture | Selectively flatten complex, mostly static visuals where profiling shows benefit | Cache creation, recache, texture size, high DPR and zoom consume time/memory; do not cache every node into its own texture. Interactive bounds remain independent of cached pixels. |
| ParticleContainer | Candidate for simple dense noninteractive markers/decoration | Lightweight particles lack full scene-object features; explicitly classify static vs dynamic properties and update static data when changed. Not a general interactive node/control container. |
| Culling and hit areas | Only draw visible bounds; prune decorative descendants from interaction | Culling has CPU cost and is not necessarily enabled by default. Preserve cables crossing viewport even with endpoints outside, exact hit priority, port anchors, keyboard/focus and node discovery. |
| Texture garbage collection and explicit destruction | Reclaim unused GPU resources | Engine GC is not a substitute for ownership and deterministic disposal; idle frame-driven GC may not run promptly in on-demand mode. Never unload shared live assets. |

Sources (official v8 docs; consult against the pinned version): [performance tips](https://pixijs.com/8.x/guides/concepts/performance-tips), [textures](https://pixijs.com/8.x/guides/components/textures), [Graphics/GraphicsContext](https://pixijs.com/8.x/guides/components/scene-objects/graphics), [BitmapText](https://pixijs.com/8.x/guides/components/scene-objects/text/bitmap), [render groups](https://pixijs.com/8.x/guides/concepts/render-groups), [cache as texture](https://pixijs.com/8.x/guides/components/scene-objects/container/cache-as-texture), [ParticleContainer](https://pixijs.com/8.x/guides/components/scene-objects/particle-container), [garbage collection](https://pixijs.com/8.x/guides/concepts/garbage-collection).

## Resource ownership and code quality

Design a renderer-scoped resource owner (name and interfaces provisional; avoid a god service). Compose asset/atlas loading, shared shape and font lookup, optional render-texture cache, and lifecycle/budget policies around engine APIs. Add a shader registry only when there are actual custom shaders. Use dependency injection at composition roots, explicit acquire/release or equivalent ownership contracts, and testable policies. Asset keys encode visual identity, style/theme version, relevant dimensions and resolution bucket; do not key by node ID unless the content genuinely cannot be shared. Do not include transient position, gain, selection or playhead in a shared resource key.

Separate immutable shared data (Flyweight) from per-instance transforms, selection, hover, focus, graph identity and parameter display state. A thousand identical oscillators may share a background, icon, port glyphs and font atlas but each retains its own graph-qualified identity and independent state. Use existing design tokens, parameter and port definitions, and authoritative geometry. Keep application commands and audio validation out of rendering. A view never destroys an asset still used by another view. Releasing the last consumer makes the resource eligible for eviction; active resources are never evicted by a stale callback. Define renderer/scene/graph/view scope and generation boundaries, context-loss recovery, theme replacement, navigation, disposal and fallback ownership. Cancel obsolete asset loads and reject stale results. Avoid per-node timers/listeners and per-frame allocations; pool only when profiles justify it, with reset and lifetime tests. No raw GL management or custom instancing until the normal Pixi path is measured and a specific bottleneck warrants it.

## Toolkit layout and control efficiency

PixiUI and PixiJS Layout/Yoga reduce custom code but add real retained objects, hit regions, event subscriptions and layout work. Inspect the installed version's control composition and layout invalidation behavior before choosing defaults. Reuse common control graphics, text styles, immutable contexts and theme tokens without sharing mutable per-instance widgets. Avoid one listener/ticker/subscription per property when a shared owner can supply the same behavior. Keep folded nodes free of property controls, inactive nested canvases unmounted, and update expanded controls only for relevant changes. A value-only update should not trigger layout unless its measured bounds change; use stable sizing where suitable. Avoid automatic whole-world layout on every frame or camera transform. Derive hit bounds and cable anchors from the final layout and invalidate only affected nodes and connections. Measure the extra costs of the actual toolkit stack against plain Pixi and the optimized DOM/Canvas baselines, including cold start, bundle/WASM size, layout passes, widget mount/disposal, input/interop latency, accessibility and sustained audio. Never substitute a trivial sprite benchmark for actual interactive controls.

## Rendering, layout and update policy

Use a retained scene and one scheduler. Disable redundant continuous rendering when idle; coalesce invalidations with requestAnimationFrame, stop on disposal/hidden view, resume with correct resize and fresh state. A dirty update requests at most one pending frame; invalidations during render are not lost. Visible animation/drag uses display cadence; telemetry uses the existing demand-scoped display cadence and does not change base values. No continuous rendering or update subscriptions for folded static leaves or inactive nested canvases. Render scheduling never drives musical timing.

Classify changes so a property edit does not re-layout or re-rasterize unrelated nodes. Candidate invalidation categories: transform, local geometry/layout, text, visual style, selection, connection geometry, telemetry, scene structure and shared resource revision. Moving one node invalidates only its position and incident cable geometry, plus relevant hit index/selection bounds. Panning/zooming transforms the world; do not regenerate all world geometry for camera motion. A live slider value changes the thumb/label only; a dynamic plot changes only its own bounded data. Expanding changes the node's bounds and affected anchors/cables; folded and expanded views share one property/control state and persistent real ports. Theme/DPR/zoom cache policy must be explicit; invalidate actual dependent resources, not every cache on each fractional zoom. Preserve z-order and click targets.

Evaluate coarse groups for world, static decorations, actively changing visuals and screen-space overlays; keep painter order and interaction semantics. Do not move objects between groups on every hover without measuring structural churn. Avoid one cached texture per node by default; prefer shared shapes/atlas sprites and cache only suitable static subtrees. Bound generated textures, never allocate a world-sized texture to hold a sprawling patch; estimate bytes (width x height x 4 for RGBA8 base level, before mipmaps, extra targets/MSAA and driver overhead). Track DPR and zoom-dependent memory; dispose on context loss/replacement as appropriate and rebuild from authoritative state.

Input uses centralized gesture arbitration and spatial hit testing per the [gesture registry](user-interactions.md). Use explicit bounds for controls and decorative noninteractive branches; measure index maintenance vs traversal. Pointer movement stays local, coalesced, with validated intents to C# at established boundaries. Do not delay continuous audio parameter updates or musical actions merely to wait for a graphics frame. No per-frame full graph serialization. Accessibility, keyboard focus and native input adapters remain independent of GPU resource lifetime.

## Benchmark evidence and limits

The official [PixiJS v8 launch benchmark](https://pixijs.com/blog/pixi-v8-launches) compares v7/v8 using 100,000 sprites under moving, stationary and structure-changing workloads. It is engine-published evidence of potential, not an Orbit 2 capacity claim. The stationary result (~0.12 ms v8 CPU work per frame) is particularly interesting for largely static graphs; it excludes total application work and is not a full frame-time guarantee. Simple sprite tests cannot predict labeled interactive node performance. Use the [rendering strategy comparison](https://etowahadams.github.io/pixijs-rendering-comparison/) as an optional exploratory reference, not a validated acceptance dataset.

S4b establishes an ordinary Pixi baseline; S4c must measure paired alternatives under identical visuals, interaction and devices: shared vs independently created resources, atlas vs separate textures, vector contexts vs sprites, ordinary Text vs bitmap text, selective cache vs no cache, coarse groups vs default hierarchy, culling/index on vs off, and idle vs active scheduling. Split experiments into focused slices; measure combined gains only after individual effects. Do not assume a custom technique is needed if native batching is sufficient.

Include repeated and heterogeneous folded/expanded nodes, long crossing cables, selected controls, live labels and plots, graph replacement, nested navigation, fit-all, dragging, zoom and audio playback. Use S2 fixtures and budgets, not artificially trivial rectangles. Collect median/p95/max frame gaps, CPU/main-thread and GPU timings when supported, draw calls/batch count (define method), visible/total objects, texture sources/count and estimated resident bytes, cache hits/misses/recaches/evictions, geometry builds, texture/buffer uploads where observable, interop batches/bytes, hit-test time/candidates, invalidations vs actual renders, allocation/disposal and long-session resource trends. Distinguish instrumented estimates, external browser captures and unavailable counters; never invent a portable exact VRAM or GPU timing API. Diagnostics must be opt-in, bounded and benchmarked for overhead. Use physical desktop/Android; verify identical audio and no regression in reported underruns/latency. Record fixture, engine version, browser, device, settings, DPR, warmup, repetitions, raw reports and rejected alternatives.

### Mandatory containment and upgrade policy

- PixiJS remains the preferred primary rendering engine. PixiUI and PixiJS Layout are supporting libraries with greater integration uncertainty, not global application foundations. Keep individual toolkit controls behind small Orbit-owned view components and local layout operations behind focused renderer-internal seams. Do not build an abstraction for every upstream API, expose toolkit objects to C# domain contracts, fork the libraries by default, or silently substitute a different renderer. The dedicated GPU source boundary and selected-stack decision remain intact.
- Scope Yoga to node-local or other genuinely local component hierarchies. World positioning, camera transforms, wire geometry and graph traversal must not require one giant flex layout pass. Detach inactive nested graphical subtrees instead of relying only on visibility flags; preserve DSP, graph identity, navigation and selection semantics. Folded leaves have no property widgets. Use explicit hit areas and verify noninteractive decoration settings rather than trusting defaults.
- Pin exact compatible direct versions of PixiJS, PixiUI and PixiJS Layout and a reproducible dependency lock; record Yoga/transitive versions and verify peer dependencies, browser support, build assets and released fix inclusion. For each planned upgrade, review changelogs/issues, reproduce relevant cases, run focused regression plus existing paired benchmarks using the same fixture/device/settings, and record baseline/candidate versions and evidence. No uncontrolled dependency upgrades or claims based solely on issue closure.
- Maintain a small upstream workaround register inside this documentation area as needed: issue link, affected/reproduced version, actual Orbit impact, owner, narrow implementation location, tests, replacement/removal condition and upgrade review. Prefer released fixes or focused local adapters to broad workarounds; remove obsolete workarounds after regression evidence. No speculative workaround if the issue cannot be reproduced and the contract already passes.
- S4b/S4c must use the above IDs as traceable regression targets; split into small slices and document pass/fail/not-run, locked versions, browser/device, raw metrics or test artifacts, any workaround and residual risk. Carry relevant checks into renderer-specific tests and sustained desktop/Android playback tests. S5 must review the catalogue, unresolved issues and evidence before approving production migration. Critical correctness, gesture, audio or recovery failures block approval; explicitly record any proposed scope change or owner-approved alternative. Do not claim that a green desktop run establishes Android compatibility.

## Acceptance before migration and during implementation

S3 resource ADR identifies native mechanisms selected, ownership interfaces, resource keys/budgets, invalidation propagation, group/layer decisions, interaction geometry, lifecycle/recovery, alternatives and tests. S4c resource experiments demonstrate measurable benefits and costs. S5 includes reviewed resource ADR, actual measured evidence and owner approval. Later production slices establish shared resource and scheduler foundations before migrating controls; test repeated acquisition shares resources, deleting one consumer preserves others, theme/resize invalidates only dependencies, idle does not schedule frames, concurrent invalidations coalesce, stale callbacks do not resurrect resources, context loss recovers, repeated navigation/disposal remains bounded, and interaction/audio/undo/persistence remain equivalent. Follow coding standards and 7.3.9 paired measurement policy throughout. Prefer the simplest proven design; no speculative custom rendering engine.
