# Full GPU-rendered editor — Phase 7.3.11 (planned)

[Roadmap slices](../roadmap/advanced.md#7311-gpu-renderer) · [Coding standards](../quality/coding-standards.md) · [Architecture](../architecture/overview.md) · [Performance baseline](../quality/performance.md#large-patch-editor-responsiveness-739)

## Objective and boundaries

The target is a fully WebGL-rendered visible editor (nodes in every expansion state, all ports, cables, properties, knobs, sliders, sequencers, plots, annotations, menus, workspace and piano), not a permanent HTML overlay for expanded nodes. Native browser input, file selection, clipboard, focus and accessible semantics may remain as minimal support adapters; they do not constitute a second visible renderer or a per-property DOM tree. The owner selected **PixiJS + PixiUI + PixiJS Layout** as the preferred stack to investigate and prototype. This is a technology direction decision, not authorization to add production dependencies or skip S5. Compare optimized DOM/SVG, Canvas 2D and WebGL in controlled experiments; consider WebGPU and worker/OffscreenCanvas only with measured benefit and a supported fallback. Full migration is conditional on evidence and explicit owner approval.

Maintain the C# domain/application model, command validation, stable graph-qualified IDs, persistence/history, shared timing and independent Faust/Web Audio/AudioWorklet execution. Do not migrate or optimize DSP under this milestone. Changes to audio-generation execution require the independent [7.3.10 gate](../quality/audio-engine-optimization.md). Graphical capacity is not DSP capacity. Preserve root/nested canvas semantics, current expansion contract, all real ports, design tokens, accessible workflows and the [gesture registry](user-interactions.md). Viewport culling must not hide inactive nodes as a product feature; any visible-detail reduction needs reviewed UX rules and unambiguous ports/hit targets.

## Selected technology direction and implementation rules

Use the following combination as the preferred implementation candidate. Do not replace Blazor, the graph/application model or Faust/Web Audio to adopt it.

| Layer | Preferred owner |
| --- | --- |
| Application state, validated commands, history, persistence, musical logic and interaction policy | Existing C# Application/Domain/Presentation and Blazor host |
| Renderer-neutral projection, command outcomes and stable identities | Existing authoritative C# owners, exposed through a narrow versioned bridge |
| Graphical scene, transforms, rendering, hit testing, resource sharing and scheduling | PixiJS, WebGL first |
| Common graphical controls | PixiUI (npm `@pixi/ui`); wrap only the controls actually needed |
| HTML-like declarative node/control layout | PixiJS Layout (npm `@pixi/layout`), Yoga-based flex layout |
| Orbit-specific visuals | Small composable node/port/cable components and specialized sequencer, automation and plot views |
| Native browser capabilities | Minimal host adapters for text/IME, clipboard, keyboard/focus, accessibility and files |

**Official implementation references (mandatory when working on the relevant subsystem):** [PixiJS v8 guides](https://pixijs.com/8.x/guides), [PixiUI](https://pixijs.io/ui/), [PixiJS Layout](https://layout.pixijs.io/), [Yoga layout](https://www.yogalayout.dev/), [Blazor JavaScript interop performance](https://learn.microsoft.com/en-us/aspnet/core/blazor/performance/javascript-interoperability). Consult documentation, changelogs, types and upstream source for the exact pinned compatible versions; examples in these documents are conceptual, not tested integration code. S3 must verify package names, peer dependencies, version compatibility, license, browser/Android support, build and WASM asset loading (including Yoga), bundle/startup cost and distribution on the existing GitHub Pages deployment. Do not assume that every widget, accessibility feature or CSS property is supported. Record the exact versions and any limitations in the ADR before the prototype; no dependency installation in this planning slice.

**Reuse before custom code.** Use PixiJS for scene hierarchy, pointer hit targets, transforms, resource management and native batching. Use PixiUI for supported buttons, sliders, lists, inputs and scrolling; assess each control's actual event, focus, keyboard and disposal behavior. Use PixiJS Layout/Yoga for supported flex direction, spacing, alignment and sizing instead of implementing a general-purpose layout engine. This is CSS-like layout, not HTML/CSS compatibility. Apply Orbit's canonical theme tokens and unit/range/scale definitions through small typed adapters. Native controls or a focused custom control are allowed only for documented unmet requirements; no wholesale UI toolkit, Flexbox engine, graph execution model or duplicate application store. Keep toolkit-specific types private to the GPU root, and never require a second UI framework such as React.

**Interaction and state:** keep application and interaction policy in C# where practical and reuse existing tests; use Pixi pointer hit testing and a single gesture arbiter. In S4b compare C#-controlled gestures with batched browser input and renderer-local transient drag/pan/slider previews, using identical semantics. Avoid per-pointer-event Blazor rendering, per-object interop and two gesture controllers competing for the same input. C# owns authoritative commits, validation, graph identity, undo boundaries and musical parameter/note semantics; JS owns view instances, layout results, local previews and GPU resources. Select the simplest measured approach that meets interaction latency and audio reliability targets. Layout-produced bounds must be the same bounds used for ports, cables, hit testing, snapping and semantic inspection. Coalesce layout invalidations and benchmark Yoga recomputation, control lifecycle, hit testing and bridge overhead separately; never relayout every node on camera movement or each telemetry update.

**Prototype sequence (isolated, not production migration):** establish one opt-in renderer entry, verified dependencies and lifecycle; build a small shared themed node shell, button, slider and layout using toolkit features; then create a representative oscillator with fold/expand, typed ports, parameter edit and connection to a second node, pan/pinch, drag and native text/focus support. Connect a controlled C# projection/intent test seam and demonstrate cancellation, undo/redo, stale revision handling, resizing, disposal and audio independence. Benchmark repeated/heterogeneous nodes and cables at the S2 sizes with actual controls and layout, not just sprites. Verify on desktop and physical Android. Split these experiments into small reviewable S4b sub-slices, each with a focused regression test and clear handoff. Prototype code is disposable until S5; do not start broad node migration or add production dependency registration beforehand. If toolkit compatibility or performance is inadequate, record evidence and revisit Canvas 2D, hybrid HTML/canvas or optimized DOM/SVG with the owner rather than silently switching stacks.

### Upstream dependency risk controls

The [upstream issue and regression catalogue](gpu-renderer-optimization.md#upstream-issue-research-and-regression-catalogue) records user-reported failures in the selected stack and their Orbit-specific tests. Treat these as candidate regression cases, not confirmed defects in the eventual locked versions. No speculative broad wrappers or library forks.

## Mandatory source-tree and dependency isolation

The GPU editor is a distinct presentation subsystem, not a collection of modifications scattered through the legacy Razor editor. Reserve **`src/Orbit.GpuRenderer/`** as the single dedicated source root for all new renderer-specific implementation, including experimental backends, browser code, interop adapters, view components, assets and renderer-specific diagnostics. This root is mandatory; the internal layout below is a proposed organization to refine during S3, not permission to create empty scaffolding or adopt unnecessary layers. Prefer a separate project/package under that root where compatible with the existing .NET/browser build; the S3 ADR must establish the exact build, module, asset-publication and project-reference boundaries before production implementation. Keep tests under a correspondingly dedicated test root (for example `tests/Orbit.GpuRenderer.Tests/`); shared browser test runners may invoke renderer-specific suites without mixing their implementations into legacy tests.

```text
src/
  Orbit.Domain/              # unchanged graph invariants and node definitions
  Orbit.Application/         # shared commands, snapshots, services
  Orbit.Presentation/        # genuinely shared renderer-neutral policies
  Orbit.Audio/               # unchanged Faust DSP
  Orbit.Infrastructure/      # unchanged audio and persistence adapters
  Orbit.UI/                  # existing host and legacy HTML/SVG renderer
  Orbit.GpuRenderer/         # NEW: one isolated renderer source root
    Contracts/               # renderer-specific boundary types
    Interop/                 # narrow host bridge and lifecycle
    Browser/
      Core/                  # renderer, camera, scene, scheduling
      Components/            # reusable graphical primitives
      Nodes/                 # node presentation and specialized views
      Connections/           # port and wire views
      Interaction/           # gesture arbitration and hit testing
      Resources/             # textures, geometry, fonts, asset ownership
      Workspace/             # GPU shell, menus, dialogs and piano
      Diagnostics/           # renderer-specific instrumentation
      Assets/                # renderer-owned source assets
      Prototypes/            # isolated comparative experiments
tests/
  Orbit.GpuRenderer.Tests/   # renderer-specific test source
```

**Allowed dependency direction:** the existing UI composition root selects and mounts a renderer through a narrow, reviewed lifecycle/intent/projection boundary. The GPU subsystem consumes authoritative shared application and presentation contracts and communicates with browser APIs through its own adapters; it never depends on legacy Razor components, their DOM measurement logic, CSS, or internal JS helpers. Domain, Application, Audio and Infrastructure must not depend on the GPU subsystem, PixiJS, WebGL or GPU-specific types. The legacy renderer must not import the GPU implementation. Shared renderer-neutral contracts belong to the existing authoritative owner (normally Application or Presentation), not a duplicated model in either renderer. No circular references or service locator coupling. Only the composition root and a deliberately small host/mount adapter may know which backend is active.

**File-placement rules:** never place new GPU implementation files in existing `Orbit.UI/Components`, legacy JS/CSS folders, audio runtime modules or unrelated projects simply because a similar feature already exists there. Do not copy or fork entire existing UI, graph, validation, persistence, timing, design-token, or telemetry implementations into the GPU root. Reuse shared policy via its canonical owner. If a missing renderer-neutral seam requires a change outside the GPU root, isolate the minimum enabling change in a focused, documented slice with its own regression coverage and explain why the existing contract is insufficient. Host registration, build configuration, dependency manifests, test runner integration, routing docs and generated distribution assets are explicit limited exceptions; keep publication paths namespaced (e.g. `gpu-renderer/`), with one source of truth and no hand-edited duplicate bundles. Prototype entry points must be opt-in and must not load or initialize the GPU engine in the normal legacy path.

**Coexistence and migration:** keep the legacy renderer independently usable throughout migration and A/B comparisons; one authoritative patch/session and one active interactive renderer at a time. Switching or context recovery disposes obsolete listeners, subscriptions, GPU resources and frame callbacks, and must preserve graph identity, history, playback and persistence. Do not refactor legacy internals merely to imitate the new renderer. Shared extractions must be justified by actual consumers, not speculative abstractions. Removal of legacy code is a distinct, approved final cleanup after parity and benchmark gates.

**Enforcement:** S3 must record the directory tree, allowed dependency graph, public contracts, host/build integration, and ownership exceptions in an ADR. Before the first production slice, add focused structural checks for forbidden imports/project references, GPU files outside the dedicated source root (with explicit reviewed exceptions), and absence of GPU dependencies in Domain/Application/Audio or the legacy backend. Test independent renderer mounting/disposal and the unchanged legacy path. Apply these checks to later GPU PRs alongside existing pre-CI test-impact review; a directory name alone is not architectural isolation. The owner-approved root is fixed unless a later explicit decision changes it.

## Candidate system boundaries and patterns (evaluate, do not blindly implement)

| Boundary | Responsibility and candidate pattern |
| --- | --- |
| Domain/Application | Existing validated commands, immutable graph snapshots, domain events and history remain authoritative; Command and explicit query/projection separation. No dependency on renderer or browser APIs. |
| Presentation projection | Renderer-neutral graph-qualified scene description and shared geometry, parameter mapping and token semantics. Immutable/versioned snapshots plus incremental change sets; adapter/mapper only where necessary. Reuse existing owners; define one geometry source for drawing, hit tests and snapping. |
| Renderer backend | Narrow lifecycle/render/resize/update contract; Strategy/Adapter for existing DOM and experimental backends, injected at composition root. Do not abstract unrelated UI or force feature-specific logic into the generic renderer. |
| Scene and components | Retained scene graph and composition of reusable controls; evaluate Composite for visual hierarchy, reusable component/layout primitives and focused controllers. Prefer stable IDs, explicit z-order and ownership. Scene nodes are visual projections, not domain nodes. |
| Input | Explicit interaction state machines for pan, pinch, drag, wire, selection and parameter gestures; centralized capture, priority, focus and cancellation; dispatch validated application commands at existing commit boundaries. Native input/IME/accessibility adapters delegate to the same intent path. |
| C#–JS boundary | Versioned, batched deltas and typed intents; bounded queues/coalescing, stale revision rejection and full snapshot recovery; no per-frame full-graph serialization or per-object interop. Transient pointer previews remain local; preserve exact undo and continuous parameter/audio-action semantics. |
| Telemetry | Demand-scoped subscriptions/Observer only for independent consumers, coalesced latest display snapshots and generation-qualified data; no per-sample UI messages, no stale value presented as live. Close hidden/nested consumers and release taps through existing owners. |
| GPU resources and scheduling | Explicit scoped ownership/disposal of buffers, textures, fonts, caches, listeners and frame callbacks. Spatial indexing, batching/instancing where useful, bounded cache, dirty flags, on-demand scheduling. Evaluate pooling/flyweights only if allocation profiles justify them; test resource recovery. |
| Native/browser adapters | Focus/accessibility, input/IME, clipboard, files, pointer capture and context loss/visibility lifecycle, separate from scene and domain. Progressive fallback, no second business-logic implementation. |

Use existing C# DI and project dependency directions. Prefer typed TypeScript for the Pixi adapter, subject to the S3 ADR and existing toolchain compatibility; assess all three packages, module organization, build/deployment integration and deterministic asset versioning. Avoid React and unnecessary new frameworks. Rendering and input preview may be local to JS; authoritative graph edits, validation and history stay in C#. Determine how shared layout, theme and hit geometry are represented without duplicating policy. Prefer explicit interfaces only at real boundaries and unit-test deterministic state/geometry independently of GPU. Never let rendering await audio samples or drive the musical clock.

## Risk register and mitigation requirements

This is a preliminary qualitative assessment, not measured probabilities or proof of defects. S1 must reconcile it with actual source and tests, assign an owner and evidence/verification target for each risk, and record unresolved risks. S3 must resolve high-impact design questions in reviewed contracts/ADRs; S5 must review residual risks and evidence before owner approval. Keep this register current as experiments and migrations reveal new issues. Do not begin porting individual nodes until the relevant foundational contracts and regression tests exist.

| Risk | Priority | Failure mode and required mitigation |
| --- | --- | --- |
| C#–renderer synchronization | Critical | Stale acknowledgments, out-of-order updates, reverted values, incorrect undo or nested graph edits. Use versioned projections, graph-qualified identity, explicit command outcomes and preview reconciliation. |
| Audio reliability under UI load | Critical | CPU contention, delayed control messages, allocation/GC, memory pressure and thermal throttling can interrupt audio despite AudioWorklet separation. Test simultaneous editing and playback; no DSP or clock coupling. |
| Custom UI framework complexity | Critical | Recreating HTML/CSS, accessibility, focus, text editing and responsive layout increases maintenance burden. Reuse PixiUI and PixiJS Layout/Yoga with a small Orbit-specific component library and native adapters; implement only missing controls. |
| Persistence and command compatibility | Critical | Existing patches or undo history may become incompatible, or transient view state may be persisted as authored graph state. Keep authoritative formats, IDs, validation and command boundaries; require round-trip and parity tests. |
| GPU resource exhaustion | High | Unique textures per node, high DPR, excessive render targets and unbounded caches consume memory. Prefer sharing, conservative explicit budgets and deterministic release. |
| Rendering regressions | High | Repeated triangulation, batch rebuilds, masks, filters, scene traversal, text uploads, per-frame allocations or idle renders negate GPU benefits. Follow the [optimization guide](gpu-renderer-optimization.md) and measure paired alternatives. |
| Interaction and geometry | High | Conflicting gestures, wrong coordinate conversions, cable/port drift, bad hit areas or accidental edits. Single transform and geometry contract; centralized gesture precedence and cancellation. |
| Mobile compatibility and sustained load | High | Device-specific drivers, DPR, shared memory, backgrounding, keyboard resize, touch and heating affect reliability. Test real mobile devices, not only desktop emulation. |
| Coexistence and migration | High | Tight coupling, duplicated policy, long-term parallel maintenance and feature gaps. Enforce dedicated roots and one active renderer, feature parity matrix, reversible migration and explicit legacy retirement. |
| Testing and accessibility | High | DOM-selector tests cannot directly locate drawn controls; visual snapshots miss functional and semantic regressions. Maintain semantic inspection, actual input tests and native accessibility support. |
| GPU context loss and recovery | Moderate (high impact if no fallback) | Driver reset, memory pressure or competing GPU activity can make rendering unavailable. Preserve application state and recover or use the existing renderer. |
| Dependency and build integration | Moderate | Version mismatch, unsupported graphics backend, stale static assets, larger bundles or broken deployment. Pin versions, audit licenses/browser compatibility, namespaced output, versioned assets and opt-in initialization. |
| Overengineering | Moderate | Unnecessary generic abstractions, custom batching or excessive framework features increase cost and complexity. Prefer engine-native functionality and documented, measured needs. |

### State synchronization and transaction protocol

Before production integration, specify the interop message schema, protocol version, renderer/session generation, graph-qualified IDs, appropriate graph/presentation revision streams, ordering and command/gesture correlation IDs. C# remains authoritative for committed state, validation and history; JS owns temporary pointer previews and the visual projection. Define snapshot handshake, incremental deltas, acknowledgment/rejection, stale and duplicate update behavior, gaps/resynchronization, invalid payloads, cancellation, disposal and bounded/coalesced queues. Do not silently drop committed edits or replay a non-idempotent command on retry. Distinguish coalescible visual updates from ordered musical actions, graph commits and continuous parameter semantics. A stale revision or old scene generation must not overwrite a newer preview or affect a different nested graph. Rejected or canceled edits reconcile to the authoritative state, not an invented successful value. Verify overlapping edits, out-of-order callbacks, duplicate delivery, deletion during drag, undo/redo during updates, switching composites, snapshot recovery and renderer switching. Preserve transaction boundaries: one intended undoable edit, no phantom graph mutations on pointer cancellation, no unnecessary recompilation.

### Geometry, input and component library contracts

Document browser CSS pixels, framebuffer/device pixels, viewport, graph/world, node-local and control-local spaces; define forward/inverse transforms, zoom anchor, DPR, resize, nested graph boundaries and rounding rules. One authoritative layout/anchor geometry per rendered view must feed drawing, ports, cables, snapping, hit testing, selection, accessible bounds and semantic test inspection. Use existing renderer-neutral geometry where suitable; do not duplicate policy in JS and C#. Test transform round trips, extreme supported zoom, touch/mouse offsets, resize, crossing cables, folded/expanded port anchors and layout changes. Preserve the [gesture registry](user-interactions.md): central arbitration, pointer identity/capture, thresholds, priority, pinch takeover and cancellation on focus/context/visibility changes. No competing per-node input handlers that bypass the shared policy.

Specify reusable controls (labels, buttons, sliders/knobs, menus, scrolling, tooltips, focus and layout) before broad node migration. Inventory supported PixiUI controls and PixiJS Layout primitives; explicitly justify each custom fallback or extension. Define their input/output contracts, design-token usage, accessibility, disabled/hover/selection states, editing and error behavior, lifecycle and resource ownership. Compose ordinary nodes from shared definitions and controls; use specialized views only where necessary (sequencers, automation, plots). Native browser adapters handle text selection, IME, mobile keyboards, clipboard, file selection and assistive semantics; do not recreate a general-purpose browser widget framework or a second graph editor. Test keyboard navigation, focus order, screen reader labels, touch targets, responsive layout, text entry and localization at multiple zoom/DPR settings.

### GPU resource budget and sustained operation

Use the [resource management and rendering guide](gpu-renderer-optimization.md) as the authoritative optimization contract. S2/S3 must set device-specific limits for estimated texture/render-target memory, cache growth, allocation/rebuild rate, update cadence and frame/CPU budgets; report unsupported measurements explicitly rather than claim exact VRAM. For RGBA8 at 260 x 240 CSS pixels and DPR 2, one cached node needs about 0.95 MiB of base pixels (1,000 separate textures about 952 MiB before driver overhead, mipmaps or extra buffers). This illustrates why default per-node raster caching is unsafe; it is not a measured Orbit memory footprint. Share immutable resources, restrict cache generation to justified static content, handle memory pressure with bounded eviction of unused assets and never evict live shared resources. Establish low-resource behavior with reviewed visual/interaction parity, not silent node or port hiding.

Add long-duration physical-device workloads (proposed 30–60 minutes, exact duration and budgets agreed in S2), on reference desktop and Android. Include sustained audio playback with repeated editing, navigation, zoom, changing plots and controls, graph load/unload, foreground/background and resize. Compare cold and warmed runs, frame-gap distributions, CPU and memory trends, input/control latency, resource cleanup, battery/thermal indicators when observable, and audio underruns or other available reliability evidence. A smooth UI with worse audio is a failed candidate. Do not interpret absence of an unsupported underrun counter as proof of glitch-free audio; retain listening/recording or other appropriate independent evidence. Avoid modifying DSP to mask renderer costs; the separate 7.3.10 gate remains mandatory.

### Renderer recovery, migration and rollback

Design explicit lifecycle states for initialization, active, suspended/context lost, restoring, failed and disposed. On context loss stop scheduling frames and GPU work, cancel incomplete interactions safely, invalidate resource handles, preserve the authoritative session, saved patch, history and independent playback; do not automatically restart or reset audio. Recover resources from the latest valid projection, reject callbacks from obsolete generations and resume only after successful reconciliation. Define bounded retry and a recoverable error/fallback path if initialization or restoration fails. Use supported WebGL context-loss simulation (see [MDN WEBGL_lose_context](https://developer.mozilla.org/en-US/docs/Web/API/WEBGL_lose_context)) and real browser lifecycle tests; consider unsupported devices, driver errors, hidden/resumed tabs and failed asset loads. Verify single active subscriptions/listeners, unchanged graph/audio revisions for presentation-only transitions, preserved history and no leaks on repeated switching/recovery.

Maintain a source- and test-linked feature parity matrix from S1 onward: each existing behavior, shared owner, old/new implementation status, acceptance check, evidence and known gap. Cover all node types and dynamic ports, expansion, parameter semantics, wiring, selection, nested graphs and macros, annotations, presets, persistence, undo/redo, sequencers, automation, keyboard/transport, visualizations, workspace and accessibility. Shared tests should exercise the same observable contract against both backends; do not mark parity from screenshots alone. Retain opt-in renderer selection and rollback until approved final parity, physical-device comparisons and cleanup. Do not ship incomplete functionality as equivalent, or change existing patch formats just to support the GPU view.

### Testing strategy and pre-migration acceptance

Audit actual existing tests and selectors before implementation. Design a renderer-neutral, read-only semantic inspection seam for test tooling: stable graph-qualified object IDs, roles, bounds in defined coordinates, visible/enabled/selected/focus state and displayed values as appropriate. Keep it scoped to test/diagnostic use with no graph mutation, no direct dispatch shortcuts and no independent domain logic. End-to-end tests locate graphical controls via semantic bounds but exercise real browser pointer/touch/keyboard interactions, then assert authoritative state, history and visible feedback. Do not replace behavior checks with renderer-internal assertions. Use deterministic unit tests for transforms, layout, gesture and resource policies; protocol/contract tests for revisions and lifecycle; published browser interaction and native accessibility tests; tolerant visual regressions with fixed fonts/DPR; architecture boundary checks; context recovery and long-session tests; paired performance/audio tests. Existing runtime CI and pre-CI test-impact review remain mandatory.

S3 deliverables must include the updated risk register, synchronization contract, geometry and component library contracts, resource budget/ownership ADR, recovery/rollback protocol, semantic test interface design and parity matrix. S2/S4 establish reproducible tests, resource and performance evidence; S5 reviews these artifacts, remaining risks and explicitly approved trade-offs before production migration. Split each oversized design or implementation task into small independently reviewable slices; do not waive correctness to reduce scope.
