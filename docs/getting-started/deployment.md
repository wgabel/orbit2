# Deployment and browser release diagnosis

[Project README](../README.md) · [Development checks](development.md) · [CI workflow](../../.github/workflows/build-and-deploy.yml)

The main-branch GitHub Actions workflow builds and tests the graph, Faust DSP, UI tokens, browser playback and published static assets. It deploys `publish/wwwroot` to GitHub Pages at [Orbit 2](https://wgabel.github.io/orbit2/). The Pages job is serialized and checks the current main runtime inputs before deployment; the original ordering guard was introduced in [PR #67](https://github.com/wgabel/orbit2/pull/67).

### Workload deduplication acceptance for S3

The first candidate is the overlap between the ordinary 50-node idle/pan/zoom workload and the all-expanded expansion matrix. Before reusing a result, prove identical saved fixture, viewport, playback and revision, eligible/expanded IDs, instrumentation, warmup, sample duration and preceding interaction state. If they differ, retain both or explicitly redesign a matched workload with separate provenance. Do not equate render-count, folded-resource or composite telemetry passes with uninstrumented timing: those passes have distinct assertions and initialization contracts. Repeated setup may be removed only when fresh-context isolation or a verified reset preserves all necessary state and cleanup checks. Preserve raw report compatibility and list all retained regression assertions; time changes separately from application performance claims.

**S3a audit and implementation:** Standard editor-50 idle/pan/zoom is not equivalent to the expansion-matrix all-expanded pass: the matrix explicitly verifies the expansion IDs and settles before timing; the ordinary playing pass follows a stopped drag and reversible parameter edit, and its revision/history differ. Neither observation is removed or reused. Render-count, folded-resource and composite telemetry runs retain separate instrumentation and their distinct assertions.

The [bulk expansion helper](../../scripts/benchmark-expansion-state.mjs) consolidates the redundant per-frame browser state reads in expansion-matrix transitions and folded-resource bulk setup/restore. It takes two full snapshots per transition (before and after), plans only required changes in eligible order, and awaits the real toggle's requested state after every click. Invalid/missing/duplicate frames, invalid toggle state, a failed wait or an incorrect final state fail the run. The matrix retains its four cases in both playback states, final restore, 1s settling and all measurement windows. Folded resource assertions, monitor sampling, single-node transitions and scope cleanup remain unchanged. No instrumentation is mixed, no report schema or settings are changed, and the helper is included in the harness fingerprint.

For N eligible nodes, the matrix previously used N individual reads plus a final state read per transition; it now uses two bulk reads. This is a reduction in browser round trips, not a measured wall-time speedup. `EDITOR EXPANSION SETUP` and `EDITOR FOLDED SETUP` logs expose actual changed-node and snapshot counts. [PR #203](https://github.com/wgabel/orbit2/pull/203) merged after [full CI](https://github.com/wgabel/orbit2/actions/runs/46137850684) passed at implementation head `d8dd2dbe7af6746421f3a883a20220cff2e5a420`. The ten 49-eligible-node matrix transitions used 20 bulk snapshots instead of 500 individual/final reads, with the original 196 actual toggle operations and 24 timing windows. Folded-resource setup and restore each changed 48 nodes with two snapshots. Four helper tests passed and all reports were produced.

Keep full diagnostic reports and standalone CLI/historical pairing available; do not relabel an abbreviated run as a full timing report. Define explicit coverage requirements and tests before switching regular runtime CI to a shorter plan. In S5, independent diagnostic jobs may be scheduled/selected by conservative change impact and run against the exact published artifact; unknown or mixed impact must fail closed to full applicable coverage. No CI execution policy changes in S3b.

### S4a shared correctness-only editor windows

The [editor window executor](../../scripts/benchmark-editor-window.mjs) owns the shared action/settle sequence and deterministic render-count assertions. The [editor runner](../../scripts/benchmark-editor.mjs) attaches its existing rAF/long-task/CDP collector only for the full benchmark. The opt-in standalone `node scripts/benchmark-live.mjs --editor-regression <fixture-directory> <regression-report.json> [profile IDs]` invokes the same actions, viewport, import, expansion/navigation, playback, counter checks, lifecycle probes and Stop cleanup as `--editor`; it does not open a CDP performance session or install frame/long-task timing observers. This first slice intentionally retains all waits and repetitions, including post-action settling and liveness intervals. It does not claim a shortened full CI path yet.

The correctness-only report uses `kind: external-editor-regression`, `settings.timingCollected: false`, and per-fixture `checks` (state/workload/expansion, render counters and parameter access when applicable) instead of timing `measurements`. It retains fixture SHA, harness SHA, revision, environment, initial/final geometry and existing lifecycle results, but omits import/play wall metrics and per-window FPS, frame gaps and CDP deltas. The paired benchmark comparator accepts only the full benchmark kind. Existing full reports and historical CLI behavior are retained.

Each report uses a distinct `regression-` filename prefix and correctness-only kind; the original benchmark reports, fixtures, settings, environment flag restoration, instrumentation boundaries and error propagation are unchanged. `EDITOR REGRESSION SUITE WALL/TOTAL` logs expose execution wall times without overwriting ordinary timing logs.

The [independent acceptance inventory and validator](../../scripts/validate-editor-regression-suite.mjs) require eight report pairs, nine profile contexts, 82 action-window identities and the named composite/folded lifecycle sequences. They check exact fixture hashes, revision, harness, environment, settings and expansion/navigation identity; both modes must independently satisfy the expected operation list, so matching incomplete results cannot pass. Regression reports cannot carry timing-window fields or masquerade as performance reports. The shared runner continues enforcing deterministic render, revision, geometry and resource assertions; the validator checks the existence and coverage of the resulting evidence, not equality of nondeterministic render counts or durations.

During S4b validation, CI continued to run the full diagnostic suite for every runtime change. For harness-changing PRs the bounded shadow expanded to the complete correctness-only suite using the exact same published build, saved fixture files and hosted runner, then invokes `node scripts/validate-editor-regression-suite.mjs <fixture-directory>` before uploading both report sets. Unit tests cover plan equivalence, missing coverage in both modes, wrong fixture/scope/provenance, unexpected timing metrics, missing counters and missing lifecycle steps. This shadow is temporary parity validation overhead, not the proposed steady-state CI policy. All existing waits are retained: the only removal is optional per-window performance collection from correctness-only mode; reducing liveness/stability delays or repeated diagnostic work requires an explicit equivalent assertion contract. S4c will address DSP and the change to regular CI.

### S4c.2 regular CI execution policy

The [runtime/deployment classifier](../../scripts/ci-change-scope.mjs) now emits a separate benchmark mode; existing runtime classification and deployment freshness rules are unchanged. Documentation-only changes still skip runtime work. In S4 all runtime builds still executed the graph/domain/presentation/Agent Kit/compiler/browser functional tests, the complete offline render checks, live playback lifecycle and all eight editor scenarios. Only optional timing collection differed. S5 introduces the narrower editor-suite exemption below.

| Mode | Selection | Evidence |
| --- | --- | --- |
| `regression` | Ordinary recognized PR runtime paths in src/, tests/ or tools/agent-kit/ (with optional docs), not identified as performance-sensitive or harness changes | All verified regression-mode reports |
| `full` | Main push/manual/unknown event, unknown or missing change data, explicit PR label `performance-diagnostics`, or changes in canvas presentation/UI or audio/DSP hot-path directories | All full timing reports, including deterministic checks |
| `both` | PR touching benchmark runners/validators/tests or the build workflow or classifier | Both sets and mandatory parity validators |

The classifier is deliberately not a semantic performance-impact analyzer. The automatic hot-path selection is conservative but not exhaustive; label any performance-related PR `performance-diagnostics` (label changes trigger CI), or run the historical paired workflow when the existing optimization acceptance contract requires controlled before/after evidence. Manual Build and deploy runs use full diagnostics; deployment permissions and freshness remain unchanged. Harness changes take precedence over other modes. Missing or unexpected Git/event data falls back to full, and an invalid emitted mode fails the build. No parallelism or selective removal of deterministic scenarios is introduced in S4.

The existing editor/DSP artifact names, saved fixtures and full-report names are retained when timing runs. Regression-only artifacts contain `regression-*.json` editor reports plus `offline-regression.json` and `live-regression.json`; their distinct kinds are not accepted as quantitative timing evidence. Both-mode runs upload both sets after successful parity. S5 will move independent required checks off the sequential critical path while retaining one exact build artifact and all required coverage. S4c.2 itself is a harness-changing PR and exercises both modes; do not infer normal-PR wall-time improvement from that run.

### S5 subsystem-aware test selection and roadmap checkpoints

The editor-suite decision is separate from runtime/deployment classification and benchmark mode. It is derived from the entire PR merge-base diff (including both sides of renames), not from its title, slice identifier or an agent's assertion. S5a exempts only changes consisting entirely of flat Python modules under `tools/agent-kit/orbit2/` or the offline Python tests/fixture generator under `tools/agent-kit/tests/`, optionally with known documentation. The build workflow independently runs Python tests, generates fixtures and validates them through the native C# importer. The eight editor benchmark scenarios use their separate C# probe-generated fixtures; the offline Python library is not part of the published editor. All other runtime checks including browser graph/published editor playback, live DSP, offline DSP, native imports and compiler tests still run. Omitted editor-suite artifacts are not uploaded or replaced by fake timing reports; the workflow records the reason in its log and job summary. The existing required build check and main deployment guard are unchanged.

In S5a all other runtime PRs retained the complete editor suite, including native exporter changes. S5b extends the audited exemptions below; shared graph/serialization, DSP/compiler runtime, UI and unknown or cross-family paths still require the editor suite. Full/both benchmark mode always requires the editor suite, including main/manual runs, harness changes, performance-sensitive paths, missing history or malformed labels. A `full-verification` PR label selects full benchmark mode and restores the editor suite; harness changes still select both. The existing `performance-diagnostics` label also forces full coverage. Neither label grants an exemption. Label changes trigger the existing workflow. Missing editor output defaults to executing the suite. A positive omission is checked against the exact reason and regression mode before accepting the skipped step.

**Roadmap checkpoint contract:** for each multi-slice feature, specify the expected affected subsystems and focused verification in each slice, plus explicit full-verification checkpoints at the first shared/runtime-to-editor integration, user-facing behavior integration, and final end-to-end milestone (combine checkpoints if they coincide). When opening a runtime checkpoint PR, apply the `full-verification` label as soon as the PR exists (before relying on its CI); preserve it during updates and verify that the relevant run actually exercised the full suite. For a documentation-only closeout, retain the prior full verified runtime revision or use a manual full run; do not pretend a docs-only check covers runtime. Agents may not use roadmap status, a skip label, PR body or title to waive automatic gates. An earlier internal-only slice may omit the editor suite only when the classifier positively proves an audited isolated scope. Shared dependencies or uncertain scope require broader coverage. Record the selected/omitted suites and reason with the real CI evidence in the owning PR and roadmap closeout. S5b will expand the audited allowlist only where dependency evidence and representative CI establish safety; S5c addresses independent parallel jobs.

### S5b native subsystem impact audit

The published UI directly references Application, Presentation, Infrastructure and Audio; Application references Domain, Presentation and Audio reference Application, and Infrastructure references Application. These are one-way architectural dependencies, not proof that a leaf change is editor-independent. In particular, Faust compiler source is generated by the actual registered emitters; `EditorBenchmarkFixtures.cs` constructs real oscillator/filter/gain/sequencer and grouped graph fixtures and compiles them before and after native serialization. The live renderer checks compiler and playback contracts; dedicated compiler tests exercise effects such as distortion and resonator at 44.1/48 kHz. A DSP-only test is not a substitute for shared graph/telemetry/voice or editor lifecycle coverage. The audit found no sufficient path-only proof to exempt production `src/` files generally. Do not blanket-exempt a whole compiler, graph or DSP directory or infer isolation from a roadmap slice name. A genuinely isolated native precursor should be developed in an independent tool or test assembly with targeted tests where architecturally appropriate, not moved out of the application solely to bypass CI; integration restores full coverage.

The standalone `tools/agent-kit/exporter/Orbit.AgentKit.Exporter.csproj` references Application and Presentation; no published project or audio probe references the exporter. Both native test projects reference it and the build explicitly runs it to export contracts, generate Python fixtures and validate native imports. S5b therefore extends the editor-only exemption to the following audited families, with optional known documentation:

| Entire non-doc diff | Retained evidence |
| --- | --- |
| Offline Python package/test files (S5a) | Python tests, C# importer validation and all other runtime checks |
| Known standalone exporter C# files (CatalogExporter, CompositeTemplateExporter, ConnectionRulesExporter, PatchContractExporter, Program), optionally the Python files and four dedicated Agent Kit native contract tests | Exporter execution, both native unit suites, Python generation and native import validation |
| Flat C# files ending Tests.cs in Orbit.Domain.Tests or Orbit.Presentation.Tests only | Both native unit suites, unchanged functional/browser and DSP checks |
| Flat *.test.mjs in tests/compiler only | Real generated compiler fixtures, compiled graph and offline audio tests, unchanged functional/browser and DSP checks |

All omitted editor reports are explicitly recorded using the classified reason; no other runtime verification or deployment policy changes. New exporter filenames, project/props/targets files, audio probe files (shared fixture producer), browser tests, benchmark helpers, UI/runtime source, unrelated mixed families, unknown history, main/manual, harness changes or a full-verification/performance-diagnostics checkpoint retain the editor suite. File extensions and path roots are intentionally narrow. The full diff must fit one audited family. These are dependency-based exemptions, not a claim that every internal roadmap slice can skip the editor. S6 must measure actual focused/full CI paths before claiming wall-time savings.

## Browser release identity and cache invalidation

Every CI publish includes the Git commit and workflow run number in its editor build identity and published manifest. Versioned CSS, editor JS, audio and persistence module paths prevent stale runtime asset trees from being mixed across deployments. Startup checks an uncached manifest and requests the correct page for a mismatched deployed commit. Local builds identify themselves as `dev`; already-open tabs can remain on an older version until reloaded. See [PR #72](https://github.com/wgabel/orbit2/pull/72) and the [original implementation record](../archive/legacy-readme.md#browser-release-identity-and-cache-invalidation).

If a merged change appears absent, first check the latest **completed** Pages deployment, its commit and the build identity shown by the running editor. Verify the live fingerprinted JS/CSS before diagnosing browser cache. Do **not** clear site data indiscriminately: IndexedDB may contain saved patches.

For precise historical implementation detail, including error conditions and verification coverage, see [the archived deployment section](../archive/legacy-readme.md#browser-release-identity-and-cache-invalidation). For runtime limitations use the [current source and tests](../quality/testing.md).
