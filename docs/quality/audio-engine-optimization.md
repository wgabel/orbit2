# Audio engine optimization — evidence-first contract (7.3.10)

Status: planned; owner requires strict code analysis, design and regression tests before production optimizations. Plan recorded in [PR #130](https://github.com/wgabel/orbit2/pull/130). The [roadmap](../roadmap/advanced.md#7310-audio-engine-optimization) owns delivery status. Related: [DSP engine](../audio/dsp-engine.md), [profiling](dsp-profiling.md), [timing](../audio/transport-and-timing.md), [verification](performance-verification.md), [coding standards](coding-standards.md).

## Scope and existing facts

The editor and DSP are separate workloads. The initial code inspection found that `FaustGraphCompiler` flattens composites, and `GraphDependencyOrder` orders only dependencies of the root master, including modulation. A compiled Faust program executes in WebAssembly/AudioWorklet; the action/transport worklets handle musical timing independently of UI display polling. `FaustGraphPlaybackService`, `GraphTopology`, compiler worker/client and audio voice lifecycle manage accepted revisions, base controls and structural replacements. Base-only and source-identical changes already have reuse paths. The compiler and Faust may already eliminate some constant work; neither reachable node count nor a zero output establishes actual kernel cost. A silent or bypassed branch may still evolve internal state. These are initial observations, not a complete code audit or proof of a bottleneck. Re-audit current code and generated DSP at the revision of every candidate.

The active-canvas/expanded-node/property-pin telemetry work is owned by 7.3.9-S3b–S3d. Do not duplicate it or turn it into DSP gating. Hidden graphs must still sound exactly as authored. Observation filtering at the bridge is distinct from removing or disabling meter calculations in the DSP kernel; the latter requires this gate.

## Mandatory entry gate for every optimization

Before changing any production audio-generation, DSP scheduling, compilation or replacement algorithm for performance, complete and record **all four prerequisites** in a committed, independently reviewable analysis/design/test slice. No speculative runtime changes, feature flags that alter sound, or bundled optimization PRs before this gate.

1. **Strict code analysis:** pin the baseline SHA; inspect the actual source and relevant tests, not only documentation. Trace graph commands, flattening and dependency ordering, emitters and generated Faust/WASM (including compiler elimination), browser worker and AudioWorklet ownership, action scheduling, parameter smoothing, observation routing, accepted revision/generation checks and resource disposal as relevant. Document data/state lifetimes, cost hypothesis, correctness invariants and existing optimizations; identify unknowns rather than guessing. Identify whether operations happen per sample, block, event, graph revision or UI tick.
2. **Measured baseline:** preserve exact fixture JSON, source hash, seed/event schedule, toolchain and browser revision, hardware, sample rate and actual quantum, transport and observation state. Use repeated offline 44.1/48 kHz runs and representative real-time desktop/Android workloads; retain raw artifacts and scope labels. Isolate UI, DSP, JS/interop, compilation and replacement costs; profile paired graph variants and account for instrumentation overhead. Use the existing 7.3.4 and 7.3.8 workflows. Unsupported metrics are unavailable, not zero. If physical-device data is unavailable, document the blocker; no unsupported capacity or real-time benefit claims.
3. **Technical design and review:** identify the smallest measurable improvement, affected code and interfaces, alternatives (including doing nothing), state/timing semantics, numerical error budget, lifecycle and failure handling, backwards compatibility, resource bounds, rollback path and explicit go/no-go criteria. State whether sample-exact equivalence is expected; any intentional audible, phase, latency or quality difference requires explicit owner approval before implementation. Do not lower global sample rate, remove layers, change authored parameters, alter musical timing or automatically degrade quality. Record the design in the owning contract or linked candidate-specific artifact; obtain owner review before enabling production changes.
4. **Tests before implementation:** commit deterministic baseline/reference fixtures and executable regression tests against the unoptimized implementation; demonstrate passing baseline CI for correctness and characterize timing tests on controlled devices. Include the relevant cases below and confirm tests exercise the proposed failure mode rather than simply checking finite output. Compare the exact same inputs/events with the optimized path after implementation. Shared CI timing is diagnostic rather than a flaky speed gate. No lowering tolerances after seeing candidate output without a separately justified review.

Implementation is blocked until analysis, baseline, design and tests are documented and verified. Maintain one focused PR/slice, report exact test evidence and missing verification. Changes affecting only diagnostics or test harnesses may proceed before the gate if they do not alter synthesis or production scheduling. New music features are not globally blocked by this performance milestone, but must obey their existing DSP contracts and may not disguise unreviewed optimizations.

## Regression matrix and acceptance

- **Reference audio:** deterministic seeds for stochastic sources; sample-aligned null difference/bit-exact comparison when feasible, otherwise predeclared numerical tolerances and spectral, RMS/peak, frequency, modulation-depth and transient checks. Match latency and phase, do not align away a real timing regression. Test at multiple sample rates and actual block sizes where supported. Preserve master output with observations enabled/disabled.
- **Musical behavior:** sample-accurate triggers/gates, tempo changes, free/BPM modes, velocity, pitch, retrigger/overlapping notes, reset, long-loop timing and modulation including fast/audio-rate FM. Compare event indices and timing drift as well as audio.
- **State:** continuous oscillators/LFOs, noise seeds, envelopes, filter history, delay/reverb/resonator tails and physical models. Test silence, near-silence, zero gain, mute/bypass, modulation-driven wakeup, feedback/stateful paths where supported, first transient, parameter edits, nested composites/macros, stop/replay, failed/superseded compilation and replacement crossfade. No missing attack, spurious click or stale state.
- **Runtime:** repeated per-block duration/load where supported, p50/p95/p99 and peak, underrun evidence, real-time factor, worklet and buffer lifetime, memory and allocation/GC, compile/source generation times and peak old+new crossfade cost. Use representative sparse percussion, dense sustained ambient, layered melody, heavy effects, physical models and nested graph fixtures. Compare both editor idle and interaction. No production always-on profiling.
- **Acceptance:** a candidate must meet its predeclared correctness and meaningful performance criteria on comparable workloads, without regressions in supported timing, audio reliability or resource lifetime. Report confidence and device limitations. If the gain is not established, reject/defer the candidate; a new architecture is not the goal itself.

## Candidate design questions (hypotheses, not implementation instructions)

### Redundant work and compiled controls
Audit identical stateless expressions, transport derivations, compiler common-subexpression elimination, live control batching and structural signatures. Do not merge independent oscillators, noise streams, stateful filters or clocks solely because settings match. Determine if connection depth/choice changes can safely reuse a compiled program; existing parameter reuse and source identity must be tested before adding more. Check revision ordering and replacement state, not just compiler throughput.

### Silent voices and bypass
Reachability is not dynamic activity. Establish a conservative activity model per voice/processor: wake on accepted sample-aligned event or modulation dependency; preserve or correctly advance state; run tails until a validated completion condition. Distinguish explicit bypass semantics, mute and zero output. Investigate whether Faust emits actual conditional computation rather than a multiply by zero; inspect generated code and benchmark. No generic silence threshold or automatic effect-tail truncation. Continuous drones and externally modulating signals may be ineligible. Design separate candidate tests for percussive/one-shot voice sleep and bypassed stateful effects.

### Multi-rate modulation
Inventory signal contracts and classify truly static, event-rate, block-rate and audio-rate calculations. Only lower rate for an explicitly proven eligible path with predeclared error bounds, interpolation/smoothing and timing guarantees. Never blanket downsample LFOs based on apparent frequency: downstream nonlinear processing, FM, edges, pitch changes and transients may require sample-rate fidelity. Preserve sample-aligned events. Compare signal and audio outputs, aliasing, clicks and cost. Reject if sound changes without approval.

### DSP partitioning
Investigate independent execution groups only after earlier measured candidates. Compare monolithic Faust optimization, partitioned compilation/replacement, boundary copies and scheduling, shared clock/transport, graph dependency ordering, modulation across partitions, feedback constraints, crossfade/state transfer and worklet overhead. Multiple worklets do not guarantee parallel audio execution. Do not partition by composite UI structure alone or introduce extra block latency. Require an architecture decision and prototype benchmark before production use.

### Final evaluation
Repeat all accepted variants individually and together against the preserved baseline. Verify 7.3.9 editor improvements remain independent, record measured supported device limits, document rejected candidates and remove temporary instrumentation or retain only opt-in diagnostics. No claim that a target node count or CPU reduction has been achieved before evidence.
