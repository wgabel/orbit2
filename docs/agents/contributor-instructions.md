# Orbit 2 contributor instructions

## Mandatory initialization

Every Orbit 2 request, including a simple question, conversational follow-up, read-only investigation, new task, resumed slice, review, planning session and delegated task, must complete this protocol before a substantive answer, analysis, design, implementation or repository modification. Reading instructions and discovering the relevant documents is permitted during initialization.

1. Read root [AGENTS.md](../../AGENTS.md) and this contributor policy from the target branch or revision. If the environment does not discover the entry point automatically, fetch it explicitly.
2. Read the [documentation map](../README.md) and [mandatory task routing configuration](task-routing.json). Classify the task semantically using every matching route, the linked domain policies, and the [architecture routing index](../architecture/task-routing.md) or usage/music indexes as needed. Routes are additive; do not pick just one for cross-cutting work.
3. Read the actual required documents and relevant sections, not only their filenames or summaries. For code tasks consult the coding standards, relevant architecture and testing contracts; for nontrivial implementation locate the owning roadmap slice and read the work-slice protocol. For documentation changes consult the documentation conventions. Read the routed domain policies as applicable.
4. Identify the current scope, applicable constraints and acceptance criteria; give the compact [initialization declaration](compliance-reports.md#initialization-before-substantive-work) of selected route IDs, actual repository-relative paths consulted and key constraints. Report unavailable required documents. Do not fabricate a read or claim full compliance based only on a link or another agent's report.
5. Before any repository-changing work, complete the [concurrent work and slice ownership gate](work-slices.md#concurrent-work-and-slice-ownership), including current remote PRs and branch claims; do not infer availability from main or chat history alone.
6. Begin substantive work only when the applicable mandatory documentation has been consulted. If a required document is inaccessible, attempt recovery and report the blocker; do not perform affected work until resolved or the owner explicitly authorizes an exception. A genuinely new topic with no existing contract is not a blocker: consult the nearest existing contracts and identify the gap.

### Repository-first response policy

**Repository evidence is the first source for every Orbit 2 request, not just code changes.** Apply the initialization protocol before making project-specific assertions, including claims about whether a feature, reference patch, experiment, decision or document exists. Conversation memory may identify search terms, clarify the user's intent or supplement verified evidence; it must not substitute for current repository discovery. An earlier conversational answer is not proof that a document is absent or that a capability is implemented.

- **Locate and read the actual owner.** Select all applicable semantic routes, consult their required files and follow the relevant index/catalogue links to the actual feature, experiment or reference asset. When a recommended or reference file directly answers the question, reading it is mandatory for that question. For example, a request about three harmonizing oscillators or their original experiment routes through `sound-foundations` to the foundation catalogue, then the Breathing Harmonic Drone case study and, where exact patch data is requested, its linked JSON. Do not stop at a directory listing, index entry or summary when the underlying document is relevant.
- **Recover failed retrieval rather than silently falling back.** If a search, tool lookup or file fetch fails or returns no matches, distinguish that from proof of absence. Discover the correct repository-access capability and try another available authorized approach (direct path/ref fetch, directory/tree listing, alternate search terms or local checkout). Verify repository and revision. Record the attempted recovery and remaining gap; do not invent access, file paths, evidence or successful reads. If mandatory initialization or the authoritative source remains inaccessible, explicitly report the blocker before any affected answer. Only offer clearly labeled general or unverified context if it does not purport to describe repository state; do not perform blocked repository work without the owner's explicit exception.
- **Ground the response.** Link the actual consulted authoritative files/sections or reference assets for claims about existing features, experiments and decisions, ideally using the checked revision when stability matters. Use code/tests and real PR evidence to resolve discrepancies between plans and implementation. Distinguish documented facts, observed implementation, prior user feedback, proposals and unresolved uncertainty.
- **Keep follow-ups inexpensive.** For every follow-up, re-evaluate scope, target revision and applicable routes. Within the same active task, reuse previously consulted content only if it remains available in context and the relevant revision is confirmed unchanged; read new or changed prerequisites and sources before answering. Reinitialize fully for a new task, new session, resumed slice, changed revision or uncertain provenance. A short acknowledgement still requires the applicable initialization/evidence report, but need not trigger unrelated searches. Never bulk-load all repository documentation.
- **Make compliance visible.** Every user-facing Orbit 2 answer, including read-only and conversational follow-ups without a PR, must include the compact documentation report defined in [compliance reports](compliance-reports.md#completion-every-task). Disclose partial or failed initialization and actual consulted paths. Do not label an answer repository-verified merely because an earlier agent consulted the repository.

These are mandatory agent behavior rules, not a claim of automatic enforcement inside an external chat client. The existing PR compliance check validates declarations; it cannot intercept ordinary chat responses or prove actual source consultation.

### Route resolution

The [routing configuration](task-routing.json) owns the minimum named document sets; this policy owns behavioral obligations. All paths are repository-relative. The configuration includes mandatory domain policy files as well as feature documents. Read `alwaysRequired` once per task, then take the deduplicated union of `required` for every matching route. Read relevant sections; follow additional feature contracts and domain-specific rules even when the configuration does not enumerate them. `recommended` guides normal investigation; `reference` is optional unless the actual task or another rule requires it. For a roadmap task, read the relevant owning register, not all three. The `novel-topic` fallback does not replace other matching routes.

Select routes by meaning, not literal keyword matching. For example: node folding with a new gesture selects implementation, roadmap (if nontrivial), editor-ui, node-layout and interaction-change; a new pitched composition selects music, synth-voice, pitched-composition, music-theory, instrument-selection, mix-analysis (for a complete piece), and other applicable routes; a documentation correction selects documentation and roadmap when tracking a slice. New or changed scope adds routes before affected work.

Every active Markdown file must have a registered route owner and a reachable navigation path. When adding/moving documentation, update the appropriate route, owner link and any affected [coverage scenarios](compliance-reports.md#repository-wide-documentation-coverage); keep exceptions exact and justified. Do not load the coverage inventory as task context. Specific routes for genre, listener-validated foundations, instrument models and technical subsystems are additive to the broad routes. Select the narrow route whenever its trigger applies.

Optional `pathPrefixes` and `pathFiles` specify conservative, case-sensitive repository-relative directory prefixes and exact paths for deterministic changed-path checks. A matching changed path can require a route but an unmatched path never proves a semantic route is unnecessary. Do not infer gestures, music intent or all feature behavior from filenames. The [structural compliance check](compliance-reports.md#automated-enforcement) validates routing and PR declarations; it cannot prove an agent read or understood the documents. Report selected route IDs and actual paths read using the [compliance report format](compliance-reports.md).

If scope changes, resolve additional documentation requirements before affected work. On a new session or resumed slice, reinitialize against the current branch rather than assuming old instructions are current. Each delegated agent must independently initialize; the coordinator provides the entry point, task scope and target revision and collects the actual consultation report. Keep declarations short; reuse documents already read in the same task without rereading unchanged sections unnecessarily.

## Working with the repository

- Begin documentation discovery with the [documentation map](../README.md). Follow the [documentation ownership and placement rules](documentation-conventions.md) when reorganizing, adding, moving, or consolidating docs; keep one authoritative home for each contract/status and repair references. The canonical project entry point is `docs/README.md`; keep it short and navigational.
- **For nontrivial implementation, redesign or multi-part work, follow [granular agent work slices](work-slices.md):** break large milestones into small, independently verifiable roadmap slices *before coding*. Default to **one slice per agent run and one focused PR**, subject to the owner-authorized documentation continuation exception in the work-slice protocol; stop with a compact handoff and next-slice ID instead of automatically starting another slice. This applies in ChatGPT Work, Codex and delegated work. Keep necessary regression coverage and quality checks; trivial self-contained edits need no artificial subdivision.
- Respect established architectural boundaries and stable identifiers, while remaining free to propose and implement justified architectural improvements within the user's requested scope. Documentation guides decisions; it is not a substitute for engineering judgment.
- A new task may have no matching document or roadmap entry. Explore adjacent contracts and the code, design the new capability, and continue within the authorized scope. Extend the closest module or create a new one when that makes the knowledge easier to find; add or revise the index and roadmap if relevant. Do not require a separate documentation PR, a previously assigned milestone, or a fixed directory/template before beginning work.

## Pull request title prefixes (mandatory)

Every new PR must start with one or more of the uppercase, bracketed scope prefixes below. For roadmap slices, use the mandatory title format `[SCOPE] <slice ID> <short feature name>: <specific slice topic>`. Use the same short, plain-language feature name across all slices of a feature (normally 2–5 words); the topic after the colon describes only the actual slice. Do not put the colon immediately after the slice ID. When the feature is enabling a distinct originating user goal, include that goal before the feature name: `[SCOPE] <slice ID> <originating goal> – <short feature name>: <specific slice topic>`. Preserve the same goal and feature labels across related slices and handoffs until the originating goal is delivered. Derive the goal from the owning roadmap/design or explicit owner direction; do not invent a goal or repeat it when it is identical to the feature name. A later unrelated use of a general-purpose feature need not retain its earlier originating goal. For work without a roadmap slice, use `[SCOPE] <short feature or work area name>: <specific change>`; do not invent a slice ID.

- `[DOC]` — documentation, specifications, roadmap, agent instructions or other documentation-only work.
- `[UI]` — user interface, editor, presentation, interaction, canvas, visualization or UI performance changes, including their supporting tests/tooling.
- `[ENGINE]` — audio engine, DSP, Faust compilation, synthesis, modulation execution, musical timing, audio runtime or engine performance changes, including their supporting tests/tooling.

Classify by actual PR scope, not the branch name or roadmap number. Use `[UI][ENGINE]` when both runtime areas change; split independently deliverable changes into focused PRs when practical. Ordinary supporting documentation and roadmap closeout in a code PR do not require an extra `[DOC]` prefix. For shared infrastructure or tests, use the runtime area(s) they support; documentation-only process changes use `[DOC]`. If the scope expands, update the title before handoff/merge to keep it accurate. This rule applies to all agents and every newly opened PR, including fixes and refactors; do not rename historical merged PRs.

Examples: `[ENGINE] 7.4.6-S4d.2b Kick Drum – Composite Macros: Offline DSP verification`, `[UI] 6.19.5-S2a Connection amount slider: Add guarded draft commit`, `[UI] 7.3.9-S3b Node performance: Gate live parameter updates`, `[ENGINE] 7.3.10-S6 Audio engine optimization: Suspend eligible idle voices`, `[DOC] Agent workflow: Standardize PR titles`. Check the title before opening or handing off a PR. Normalize existing open PR titles when requested; leave closed and merged history unchanged.

Read those policies before substantive work; apply their conditional obligations without loading unrelated feature documents. ## Documentation and verification

- Follow the [documentation-only continuation exception](work-slices.md#documentation-only-continuation) when applicable. Documentation-only edits need no test run, CI wait or intervening merge; report them as committed without verification. Never extend this exception to executable changes.
- Prefer one authoritative technical contract with relative links from related modules; avoid duplicating detailed specifications. Preserve useful rationale, examples and historical implementation records, clearly distinguishing them from current contracts. Split or combine modules when the topic warrants it; filenames and target sizes are not rigid requirements.

## Task handoff: documentation feedback

**Mandatory for every multi-step task, regardless of size:** include the [visual progress summary](compliance-reports.md#mandatory-visual-progress-summary-for-multi-step-tasks) in every user-facing summary, including resumed slices, partial results and blockers. Show the full known plan, evidence-based statuses and next action; use the plain-text fallback when graphical rendering is unavailable.

At the end of every Orbit 2 response, including simple questions and follow-ups, follow the [completion and PR evidence formats](compliance-reports.md). Include a short documentation report in the user-facing summary (or to the coordinating agent when delegated):

- **Documentation consulted:** List the repository-relative paths of documentation and routing files actually read for the task, including this file and any selected domain policies, overview, roadmap or feature modules consulted. If only specific sections were read, indicate that when useful. Do not claim to have read files you did not inspect. If none were consulted, say so.
- **Documentation discoverability:** Report whether finding the relevant information was straightforward. Mention any missing topics, unclear navigation, misleading links, conflicting or outdated descriptions, or other search difficulties that affected the task. Say how the gap was resolved (for example, inspecting the source or tests), and flag any useful documentation improvement. If there were no difficulties, say "No issues found."

Keep this report proportionate and factual, including for read-only tasks. For every PR, maintain the cumulative machine-readable evidence block in its description; do not claim that a declaration proves actual reading. It is feedback on the documentation system, not a requirement to read additional files or a reason to delay work on a new topic. When coordinating multiple agents, collect their reports and consolidate the relevant paths and findings in the final handoff.
