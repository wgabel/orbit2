## Reading guide and current implementation

**Single roadmap authority:** This `docs/roadmap/overview.md` is the canonical cross-project status and milestone entry point. The [foundation](foundation.md), [editor and effects](editor-and-effects.md), and [advanced](advanced.md) files are **detailed milestone registers** belonging to this roadmap, not independent competing plans. For a change, update the owning register first; update this summary if its overall capability/status changes. Keep stable milestone and slice IDs; do not merge the large registers into an expensive monolithic agent context. See the [documentation map](../README.md).

**Status vocabulary:** Implemented = verified on the audited main branch or in an explicitly identified implementation PR; Partial = a defined subset delivered; In progress = implementation underway; Planned = design or future deliverable; Deferred = deliberately outside current scope.

**Granular delivery for agents (mandatory for nontrivial work):** A numbered phase or milestone is not necessarily an executable unit. Before implementation, break it into independently testable, restartable `<milestone>-S1`, `-S2`, ... slices in the relevant milestone register, using the [agent work-slice protocol](../agents/work-slices.md). Aim for one observable outcome, 1–3 acceptance checks, a focused PR and **one slice per agent run**. Record dependencies, verification and real PR status; finish with a short handoff naming the next slice. Avoid token-heavy context dumps and do not weaken quality checks. The [documentation-only continuation exception](../agents/work-slices.md#documentation-only-continuation) permits sequential owner-requested documentation slices on the same branch without CI waiting. Trivial fixes need no contrived decomposition.

**Implementation traceability (mandatory):** Every delivered feature, improvement and bug fix must cite its actual implementation pull request(s) using `[PR #N](https://github.com/wgabel/orbit2/pull/N)` directly in the relevant implementation description and roadmap entry, and in the status table when applicable. Include follow-up PRs beside the affected feature. Open the PR first if its number is not known, then update the architecture on that PR's branch before merge. Never substitute a documentation-only PR for runtime evidence or mark unmerged work as merged. Older direct-to-main implementations predating the PR workflow have no PR number; cite the actual commit when extending their implementation record. Do not invent historical PRs.
