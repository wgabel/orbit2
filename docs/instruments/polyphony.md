##### Reuse, polyphony and verification

Use ordinary composite templates with named macro-style rack inputs (`Pitch`, `Gate`, `Velocity`, `Brightness`, `Excitation`, etc., exposing only applicable ports), shared preset catalog and annotation features. For rate-dependent tuning, a pitched bank receives the same semitone signal, not one Hz amount per oscillator guessed from a UI. Phase 7.1 ADSR enables held instruments, and AD/pulses enable strikes. Begin with monophonic templates, then design a bounded polyphonic voice allocator (fixed precompiled voice capacity, explicit voice stealing/release and peak headroom). Note actions must activate existing voice states rather than add/remove graph nodes, allocate in the audio callback or recompile per key. Independent notes retain independent envelopes and resonator tails; polyphonic performance must be profiled before promising a large voice count. Hardware MIDI, sequencer-driven pitch and sample hybrids reuse the same pitch/note/action interface when available.

Keep Domain node definitions/validation independent from browser/Faust, Application contracts/commands and template registry independent from the renderer, pure pitch/coefficient math and emitters in Audio, worklet event delivery in Infrastructure, and readable projection/controls in Presentation/UI. Maintain immutable snapshot and portable persistence compatibility. Compile and render deterministic impulse/noise fixtures at 44.1/48 kHz: verify resonant center/decay T60, zero-input silence, frequency tracking, spectral ratios, stable fast modulation, independent per-mode decays, retrigger superposition, finite bounds and no unintended master clipping or instability. Test live note/gate timing, no graph mutation per note, stale events, nested racks, voice independence and bounded CPU/memory. Reuse the shared scope and spectrum for actual signal and processor response views for configured stationary response. No new sample observation channels are required for synthesis. Annotated example patches and listening checks complement, but do not replace, numerical regression tests.

## Strum note-event processor (planned, Phase 7.2.9)

Inspired by Orchid's one-shot strum performance mode, not a claim of exact hardware emulation. A single note-on or chord onset produces an ordered sweep of individually articulated chord tones across one or more octaves. A Strum node sits between a keyboard/sequencer or chord source and a compatible polyphonic instrument. It emits timed note events, not audio, a summed pitch signal, or a repeating arpeggio. A monophonic destination cannot reproduce overlapping voices; reject unsupported routing explicitly. Reuse the shared voice allocator and note-event contract from 7.2.6c; separate that dependency from optional hardware MIDI. Investigate the existing chord generator's actual contract before adapting it; do not reinterpret its scalar signals as independent note identities.

For a C major chord starting at MIDI 60, two octave repetitions in ascending order produce 60, 64, 67, 72, 76, 79, e.g. at 0, 65, 130, 195, 260, 325 ms. Each voice has independent pitch, onset, velocity, gate/release and envelope/tail. The default is one sweep per onset, with overlapping notes; no automatic looping. Preserve voicing/inversions, sort in the requested direction, deduplicate coincident pitches and skip out-of-range notes rather than clamping them into duplicates. Accept chord input or a single root with an explicitly selected chord voicing; share existing chord definitions rather than inventing a competing harmony engine.

Controls: octave repetitions (default 2), inter-note interval (ms, zero for simultaneous attacks), ascending/descending direction and held-key vs fixed-duration articulation. Held mode cancels unsounded notes on release and releases already sounding voices; fixed mode schedules each note's own gate length and can let a sweep finish after key release. Later expressive controls: alternating/random order, BPM-synchronized spacing, acceleration/deceleration, timing humanization, velocity spread/accent, note-duration variation. Apply supported continuous modulation through ordinary parameter definitions and snapshot effective bounded values at sweep onset for reproducible scheduling; discrete choices are configuration. Randomness must be seedable for offline reproduction. Keep independent event/voice identities when repeated or overlapping sweeps target the same pitch; do not let an old note-off release a new voice. Specify queue/voice limits, deterministic overflow/stealing, release and cancellation on stop/reset, disconnect, stale generation and focus-loss release-all. Use the shared audio/beat clock, preallocated bounded state, no per-note graph mutation, compilation, UI timers or callback allocations. Preserve existing mono patches, preset IDs and transport semantics.

Use the normal node registry and shared editor controls with explicit port type labels, compact important controls, ordinary persistence and a worked keyboard → chord → Strum → polyphonic instrument patch. Measure onset spacing, independent gate/velocity/tails, zero spacing, order, octave boundaries, deterministic variation and lifecycle at 44.1/48 kHz; verify browser input, save/load and bounded voice CPU/memory/headroom. Audition a plucked voice and sustained pad separately; distinguish measurements from listener approval. Delivery/status: [7.2.9](../roadmap/advanced.md#phase-729--polyphonic-strum-planned).
